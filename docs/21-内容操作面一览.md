# 内容操作面与权限设计底稿

> **角色**：工作底稿——先收 Action Universe，再筛 Archive Actions，再逼 Visibility，最后锁矩阵。  
> **不是**：现行契约（仍以 [`08`](08-发现层对象模型.md) 为准）；不是 ADR（消化后再开）；不必急着扩 `00` 链。  
> **写法**：优先补全、少丢信息；决策与开放问题堆在文末，一切活动仍在本文。  
> **日期**：2026-08-20 起。

---

## 0. 设计顺序（钉死）

| 步 | 做什么 | 不要做什么 |
|----|--------|------------|
| **1** | 收干净 **Action Universe**（所有能触及档案相关物的操作），按层次拆开 | 不要把部署 / 身份 / 音乐和文档读写成一锅粥 |
| **2** | 从中筛出真正属于 **档案权限系统** 的 **Archive Actions** | 不要把 `git pull`、壳命令硬塞进文档 ACL |
| **3** | 用 Archive Actions 的结果分布 **逼出** Visibility 需要几档 | **不要先拍** L0–Ln 数字再让权限去凑 |
| **4** | 锁 **Principal × Visibility × Action** 矩阵；各入口只实现该表 | 不要再写一堆零散 `if (public && owner)` |

**设计原则（正式）**

> 权限系统由三件**独立**的东西构成：**Principal**、**Document Visibility**、**Action**；最终是否允许 = 三者共同决定。  
> 而不是：`public/private` + `owner/member/visitor` + 一堆零散分支。

矩阵一旦锁定：HTTP、网页终端、Agent、读侧过滤、member、未来新入口——都只是在**实现这张表**，不是重新设计权限。

与 [0018](adr/0018-content-visibility-and-sync.md) 的关系：0018 已定「正文离公开 Git / publish / private 默认不上盘」；**可见性档位数与读侧矩阵**以本文后续篇章为准，消化后可修订或 supersede 0018 相关段落。本文**暂不改 ADR**。

## 1. Action Universe（操作全集）

### 1.1 命名约定

- **Action id**：小写蛇形，跨入口稳定（如 `read_body`），不跟终端命令名绑死。  
- **入口**：终端命令 / HTTP 路径 / 运维脚本——只是实现，不是 Action 本身。  
- **状态**：`✓` 已有入口 · `◇` 政策有、入口未齐 · `○` 设想中、尚无产品面。

下列按**层次**拆开。一层之内尽量穷尽现行代码与已写政策。

---

### 1.2 文档操作（Document · `DocumentRef`）

对象：`projects` / `thoughts` / `resources` 下的 markdown 文档。

| Action id | 含义 | 终端 | HTTP | 状态 |
|-----------|------|------|------|------|
| `discover_docs` | 知道有哪些文档（列表/索引投影） | `projects` / `thoughts` / `resources`；`ls`/`tree` 见文档节点 | `GET /api/v1/items`（过滤/投影） | ✓ |
| `open` | 打开阅读面（纸面 main/rail） | `open` | （详情 GET 可充当「拿到可呈现载荷」） | ✓ |
| `read_body` | 读取正文与元数据 | `cat`；`open` 后的纸面 | `GET …/items?source=local&localKey=` · `GET /api/v1/docs?path=` | ✓ |
| `search` | 按正文/标题/标签检索 | `search` | `GET /api/v1/search?q=` | ✓ |
| `find` | 按路径/名称等检索节点 | `find` | `GET /api/v1/find?q=` | ✓ |
| `create` | 新建文档 | `edit` 不存在路径 → 保存 | `PUT`（目标不存在） | ✓ |
| `replace` | 整篇覆盖（含 raw） | `edit` 保存全文 | `PUT`（目标已存在） | ✓ |
| `patch` | 部分字段更新 | （无独立命令；编辑器等价于 replace） | `PATCH` | ✓ HTTP；终端无独立 patch |
| `delete_doc` | 删除文档 | 编辑器删除 | `DELETE …/items` | ✓ |
| `change_visibility` | 改变文档可见性档 | — | — | ○ 高级管理；档位未定前不实现 |
| `publish_doc` | 把本机某文档推入部署面 public 集 | — | （写 API 直改 VPS ≈ 旁路） | ◇ 属发布，见 §1.5 |

说明：`discover` / `open` / `read_body` / `search` / `find` 在实现上常共用快照；权限模型里仍宜拆开——「能搜到标题」≠「能读全文」是经典档位差。

## 2. 哪些属于档案权限系统 → Archive Actions

### 2.1 判定规则

纳入 **Archive Actions**，当且仅当：

1. 作用对象是**档案内容或其在发现层的投影**（文档、组内目录、person/timeline 投影、索引/检索结果）；且  
2. 允许与否应随 **Principal** 与（将来）**Document Visibility** 变化；且  
3. **不是**纯运维管道（git/rsync/env）、**不是**纯壳 UX、**不是**音乐 BFF 专属域。

排除或降级：

| 类别 | 例子 | 归宿 |
|------|------|------|
| 部署管道 | `pull_code`、`publish_public`、`backup_*`、`env_secrets` | **Deploy policy**（可另有运维 ACL，但不进 Document 矩阵） |
| 身份原语 | `login` / `logout` / `issue_*` | **Principal 生命周期**（矩阵的输入，不是格子里的 Action） |
| 壳 | `help` / `clear` / `history` / `themes` / `cwd_nav` | UX；至多「help 是否列出某命令」派生自矩阵 |
| 音乐 | 全部 `music_*` | **Music policy**（已有 owner + cookie 第二闸） |
| 发布旁路 | 用写 API 直接改 VPS | 仍是 Archive `create/replace/…`，另加部署面风险说明 |

`publish_public`：**不是**文档 ACL 里的一格；是「哪些 Visibility 的文档允许进入部署面」的**发布策略**。可在矩阵锁定后用「仅 L_public 可 publish」一类规则挂钩，但 Action 本身属 Deploy。

### 2.2 Archive Actions（候选锁定表）

下列为权限矩阵将要填的行（id 稳定；档位未定前不填列）。

| Action id | 一句话 | 现行默认（实现现状，非正式 ACL） |
|-----------|--------|----------------------------------|
| `discover_docs` | 是否出现在索引/列表 | 盘上有则可见（无过滤） |
| `open` | 是否允许进入阅读面 | 同公开读 |
| `read_body` | 是否允许读正文/详情 JSON | 同公开读 |
| `search` | 是否允许全文检索命中 | 公开；命中集=全盘 |
| `find` | 是否允许路径检索命中 | 公开；命中集=全盘 |
| `create` | 是否允许新建文档 | owner UI / Bearer 写 |
| `replace` | 是否允许整篇覆盖 | 同上 |
| `patch` | 是否允许部分更新 | 仅 HTTP Bearer |
| `delete_doc` | 是否允许删文档 | owner UI / Bearer |
| `mkdir` | 是否允许建目录 | owner UI / Bearer |
| `rmdir` | 是否允许删空目录 | owner UI / Bearer |
| `read_person` | 是否允许读人物旁路 | 公开 |
| `read_timeline` | 是否允许读时间线旁路 | 公开 |
| `change_visibility` | 是否允许改文档可见性档 | ○ 无；**高级管理** |

**暂挂（是否并入矩阵，步 3 再定）**

| id | 争议 |
|----|------|
| `list_dir` / `tree` | 与 `discover_docs` 高度重叠；可能合并为「目录枚举」或视为 discover 的投影 |
| `write_person` / `write_timeline` | 无正式 API；若永远本机+publish，可只留在 Deploy；若将来 HTTP 写，再升格 |
| `capabilities` | 通常应对所有 Principal 可读；或对 write 位做差异化披露 |

### 2.3 非 Archive Actions（明确移出）

```
pull_code, pull_body✗, publish_public, publish_music_data,
backup_local, backup_server_full✗, env_secrets,
login, logout, whoami, issue_agent_token, issue_member_session,
help, clear, history, themes, cwd_nav,
music_*（整族）
```

## 3. Visibility Levels（步 3 · 先方法论，不拍数字）

### 3.1 原则

- **不要先决定**「要几个 L」。  
- 用 Archive Actions 问：是否存在「Principal A 对文档 D 允许 action X、不允许 action Y」的**真实需求**？每出现一种稳定的允许组合，才考虑加一档 Visibility（或加一种 Principal）。  
- 0018 的 `public` / `private` 是**发布与存放**直觉，**不等于**最终 Visibility 枚举。

### 3.2 用 Action 逼档位的探针（写作清单）

对每一篇（或每一类）文档问：

1. visitor 能否 `discover_docs`？能否 `read_body`？能否被 `search` 命中？  
2. 未来 member 是否需要「能读不能写」？是否需要「能 search 到但不能 open」？（后者很少见，有则可能多一档）  
3. 是否需要「有链接才能读、无链接不可 discover」？（可能逼出 link-share 档；**也可能不需要**）  
4. owner-agent 与 public-agent 是否必须分档？（倾向：是，用不同 Principal，不一定新 Visibility）  
5. `change_visibility` 谁能做？通常仅 owner → 不新增 Visibility，只约束 Action。

### 3.3 可能结果（示例，非决定）

仅作想象力边界；**未采纳**：

```text
可能：L_owner_only → L_member → L_link_share → L_public
可能：只要 owner_only + public（无 member / 无 link）
可能：member 与「部署面 private」同构，仍两档内容 + 两种 Principal
```

步 3 完成标志：写出「我们需要的 Visibility 集合」+「不需要的档 + 否决理由」。

## 4. 矩阵草图（步 4 · 占位）

### 4.1 三轴

| 轴 | 现行 | 设想 |
|----|------|------|
| **Principal** | `visitor` \| `owner`（网页）；Agent = Bearer（写）+ 匿名读 | + `member`；Agent 分 `public-agent` / `owner-agent`（或只读 scoped token） |
| **Visibility** | （无读侧字段；物理上盘=公开） | 步 3 产出 |
| **Action** | 分散在命令与 HTTP | §2.2 Archive Actions |

### 4.2 示意（数字与勾选均为假想，勿当规范）

```text
                    Document Visibility
                L0       L1       L2       L3
Principal
visitor          ✗        ✗        ✗        ✓
member           ✗        ✓        ✓        ✓
owner            ✓        ✓        ✓        ✓
public-agent     ✗        ✗        ✗        ✓
owner-agent      ✓        ✓        ✓        ✓
```

真正落地时：**每个格子不是一个布尔，而是一组 Archive Action 的允许集**（至少区分 read 族 vs write 族）。例如同一 Visibility 上，member 可能 `read_body=✓` 且 `replace=✗`。

### 4.3 实现纪律（矩阵锁定后）

- 终端 help/Tab 藏命令、Actions 硬拒、HTTP 401/403、discovery 过滤——全部是矩阵的**投影**。  
- 禁止新入口自创权限语义。  
- `change_visibility` 本身也是矩阵里的一行。

## 6. 决策与开放问题（本文账本）

### 6.1 已采纳（本文 → 已消化进 ADR 0019）

1. 运行时核心 = **Capability lattice**（`READ ⊂ WRITE`；`public < member < owner`），不是巨型三维枚举矩阵。  
2. 矩阵表仍作**测试 / 审计基准**（`permission.test.ts`）。  
3. `git pull` / 壳 / 音乐整族 / 身份签发 **不进入** Archive Actions。  
4. `publish_*` 属 Deploy；硬不变量：`selectPublishPaths` 排除 `content/private/**`。  
5. 改可见性 = 跨 zone 移动（路径派生）；无 frontmatter `visibility`。  
6. Agent = 同构 Grant 载体；Bearer scope **只约束写**，读全开（owner-agent）。  
7. **ADR 0019** 已落地；0018 离仓政策保留。  
8. Zone：`content/<group>` = public；`content/private/<group>` = private（最低可达 member）。  
9. 不可达 = 不存在（404 / 省略）。  
10. person / timeline = bypass，天生 public。  
11. member **语义已锁定**；登录入口未实现。

### 6.2 仍开放

1. `list_dir`/`tree` 是否在文档层与 `discover_docs` 合并命名（实现上已同属 read）  
2. member 登录 / 会话形态（新 ADR）  
3. 是否将来要第二类只读 Agent（另开 Actor，不改本模型）  
4. 终端 `mv` / 显式 `change_visibility` 命令  
5. 完整 publish 运维脚本（路径选择已可测）  
6. `write_person` / `write_timeline` 是否进 HTTP  

### 6.3 下一步

- [x] Archive Actions → capability 归类  
- [x] Visibility = zone（public | private）  
- [x] 公理表 + 读侧裁剪落地  
- [ ] member 登录（另刀）  
- [ ] publish 脚本定稿
